# 정책 봇의 새로운 방향성

> 노션 "정책 봇의 새로운 방향성" 페이지와 2026-10-26 검토 논의를 정리한 문서.
> 결정이 바뀌면 이 파일을 고친다. 진행 상황은 `EXPERIMENTS.md`에 적는다.

## 1. 출발점: 두 가지 답변 방식 비교

| | A. Claude가 정책 문서 + 디스코드 대화를 직접 읽고 답변 | B. 정리된 노션 DB만 검색해 답변 (현재 `@봇` 멘션 질문, 구 `/정책질문`) |
|---|---|---|
| 장점 | 별도 인덱스 없이 단순 · 멘션으로 자유롭게 질문 · **문서에 반영 안 된 최신 결정까지 잡음** (실제로 문서-디스코드 충돌을 찾아냄) | 빠름 · 토큰이 적음 (실측 1회 약 $0.015) · 결정자·근거·적용범위·미해결 질문까지 깔끔하게 나옴 |
| 단점 | 대화가 쌓일수록 시간·비용이 계속 증가 · 버려진 의견과 결정이 섞일 위험 | 정리를 안 한 결정은 존재하지 않는 것처럼 답함 · 사람이 `/정책정리`를 호출해야 쌓임 |

**핵심 진단:** B가 충돌을 못 잡은 이유는 검색 방식이 아니라 **정리가 안 돼서 노션에 없었기 때문**이다.
다만 사람이 정리를 호출하는 구조에서 정리가 늦어지는 건 예외가 아니라 항상 생기는 일이다. 그래서 보완 경로가 필요하다.

## 2. 지향하는 흐름 (결정)

**원칙: 노션 정책 문서가 기준(source of truth)이고, 답변도 노션 기준으로 한다. 디스코드는 아직 반영 안 된 변경분을 메우는 용도.**

### 2-1. 정리 (쓰기)
1. 논의가 끝난 스레드에서 `/정책정리` 호출
2. 결정 히스토리(노션 DB)에 요약 저장 — 지금처럼. `thread_id`도 함께 저장 (이미 저장 중)
3. **원천 정책서 반영 제안** (신규)
   - 해당 항목이 있으면 → 그 블록에 **댓글로 변경 제안**
   - 해당 항목이 없으면 → 맞는 섹션에 **다른 색으로 새 블록 삽입**
   - 어디 넣을지 모르면 → **페이지 레벨 댓글**
4. PM이 확인 후 원문에 반영

원문 수정 위치는 **정책 ID(예: `XX-04-03`) 단위**로 잡는다. 이 구조가 "원천 문서에 어떤 구조로 반영할지"에 대한 답이다.

#### 정리 규칙 (2026-10-26 결정, `prompts.py`)
- **상태는 말한 사람의 직책이 아니라 대화의 신호로 판단한다.** "결정 권한자(PM 등)가 확정해야 최종결정" 룰은 뺐다. 모델이 누가 PM인지 몰라서 확정된 건이 '제안'으로 남는 문제가 있었다.
  - 최종결정: 확정 신호가 있고 그 뒤 반론이 없음. 확정 신호 = 명시적 확정("확정", "이대로 갈게요", "반영해둘게요") · 확인 질문에 명확한 긍정 답 · 다른 참여자의 동의 답글 · **다른 참여자의 동의 리액션**(👍 ✅ 등, `config.AGREE_EMOJIS`)
  - 논의중: 다른 참여자의 반응은 있었지만 확정 신호가 없음
  - 제안: 한 사람이 안을 냈고 다른 참여자의 반응이 없음
  - 주의: 공지·요청 글에 달린 👍("확인했어요")도 동의로 잡힐 수 있다. 최종 판단은 승인 화면에서 사람이 한다.
- **날짜는 둘로 나눈다.** 결정일 = 그 결정의 근거 메시지 중 가장 늦은 시각(코드가 계산, 토큰 0), 정리일 = 승인 시각. 호출 시각을 쓰면 정리가 늦어질 때 과거 결정이 최신으로 보여 "최신 결론"이 뒤집힌다.
- **근거(rationale)는 대화에 명시된 이유만 1~2문장.** 경위 서술 금지, 의견이 바뀌었으면 "초기 A → B로 변경 (이유)". 완전히 없애지 않는 이유: 검색·답변 모델은 메시지 링크를 열 수 없어 "왜?"·"예전엔?" 질문에 답할 근거가 사라진다. 대신 노션 페이지 본문에 **근거 메시지 원문 발췌**(코드가 잘라 넣음)를 링크와 함께 넣어 사람이 요약을 대조할 수 있게 한다. 발췌는 검색 인덱스에 넣지 않는다.
- **외부참조는 URL만.** "시안 이미지", "피그마 참고"처럼 링크 없는 참조는 버린다.
- **확인필요는 대화에서 실제로 답이 안 된 질문만.** 모델이 엣지 케이스를 새로 만들지 않는다.
- **적용범위:** 화면·기능은 대화나 주제에서 분명하면 쓰고, 플랫폼·버전·사용자 유형은 언급됐을 때만 쓴다. "언급 없음" 같은 채우기 문구 금지.

#### 재정리·갱신 (2026-10-26 결정, Q-7 — 같은 스레드만)
같은 스레드를 다시 정리하면 기록이 중복으로 쌓이고, 반영 제안까지 PM에게 다시 간다. 같은 정책을 다른 스레드에서 바꾸는 경우(Q-8)는 아직 범위 밖.

**방향: 바뀐 결정은 이전 기록을 덮어쓰고, 이전 버전은 페이지 본문 '변경 이력'에 남긴다.**

검토한 안 (처음 계획은 ③이었다가 ②로 바꿈):

| | ① 덮어쓰기만 | **② 덮어쓰기 + 변경 이력 (채택)** | ③ 새 기록 + 대체 연결(상태 '대체됨' 또는 relation) |
|---|---|---|---|
| 노션 DB | 정책당 한 줄 | 정책당 한 줄 | 버전마다 한 줄 (필터 보기 필요) |
| 이력 | 사라짐 | 본문 + 로컬 버전 줄에 남음 | 남음 |
| 잘못 연결했을 때 | 복구 불가 | 본문·로컬 버전으로 되돌릴 수 있음 (수동) | 연결만 끊으면 복구 |
| 승인 기록 | 첫 승인자가 사라짐 | 버전별 승인자를 변경 이력에 남김 | 버전마다 남음 |
| DB 구조 변경 | 없음 | 없음 | 상태 옵션 또는 relation 속성 추가 |

- ③에서 상태를 '대체됨'으로 바꾸는 안은 원래 상태(최종결정·논의중)를 지우고, 상태 칸에 "얼마나 확정됐나"와 "지금 유효한가"를 섞는 문제가 있어 relation 안까지 검토했다.
- 팀원이 노션에서 읽기 쉬운 "정책당 한 줄"과 단순함을 택했다. 대신 잘못 덮어쓰기를 막는 장치를 승인 화면에 둔다.

흐름:
1. 이 스레드의 현재 기록(`thread_id`, 기록 ID별 최신 버전)을 찾는다. 마지막 정리 시점(`source.summarized_until`) 이후 새 메시지가 없으면 LLM을 부르지 않고 끝낸다.
2. 대화 전체 + 이전 기록(사람이 승인·수정한 버전)을 넣고, 정리 이후 메시지에는 `[새 메시지]` 표시. 스레드가 짧아(5~16개) 일부만 넣는 것보다 전체가 맥락 손실이 없다. 길어지면 그때 이후 메시지만으로 바꾼다.
3. 결정마다 `new` / `update(기록 ID)` / `unchanged(기록 ID)` 판정. unchanged는 저장·반영하지 않는다. update는 **이전 내용과 합친 현재 전체 정책**으로 쓴다.
4. 코드가 보수적으로 고친다: 목록에 없는 ID·이미 다른 결정이 가져간 ID → new, unchanged인데 상태가 다르면 → update, **이전이 최종결정인데 이번이 논의중이면 → reopen** (덮지 않고 새 기록 + "재논의 대상" 표시 → 답변: "현재 A, B로 변경 논의 중").
5. 승인 화면에 "🔁 변경 — 이전 기록 X을 덮어씀 (이전 결정)"을 보여 주고, [🔗 연결 해제]로 덮지 않고 새 기록으로 저장할 수 있다.
6. 저장: 로컬 `history.jsonl`은 append-only 유지(같은 ID의 `version` 줄 추가, 마지막 줄이 현재). 노션은 같은 페이지의 속성을 갱신하고 본문을 다시 쓴다(위: 현재 버전, 아래: 변경 이력 토글 — 버전·정리일·상태·승인자·결정·근거·근거 메시지).
7. 정책서 반영: 바뀐 기록(v2~)은 이전 버전 제안 댓글 스레드에 답글로 단다. 같은 기록·같은 버전은 다시 달지 않는다.

위험과 기준:
- **잘못 연결(유효한 기록이 덮어써짐)이 놓침(중복)보다 위험**하다. 애매하면 new, 확정은 승인 화면에서 사람이.
- 다른 스레드 매칭(Q-8)으로 넓힐 때는 정책 ID(정책서 매칭 결과)가 같은 것끼리를 같은 정책으로 본다. 주제 유사도보다 확실하다.

### 2-2. 질문 (읽기)
1. 노션 정책서 + 논의 DB를 함께 검색해 답변 (반영이 늦어진 경우 대비)
2. 그 다음 디스코드는 **"아직 정리 안 된 논의"만** 키워드로 조회
   - 대상: 정책 채널 한정 + 최근 14일 + 그 이전이라도 `thread_id`가 논의 DB에 없는 스레드
   - "논의 DB에 없을 때만" 조건으로는 부족하다. 노션에 **있지만 낡은** 경우(문서 수정 후 디스코드에서 바뀐 경우)를 못 잡는다.
3. 디스코드에서 미정리 결정을 찾으면 답변에 **[미정리 논의 있음]** 표시 + **[정책 정리하기] 버튼**
   → 질문하다 자연스럽게 정리가 일어나고, 같은 디스코드 내용을 두 번 읽는 비용이 사라진다.

이렇게 하면 디스코드 조회 비용이 누적 대화량이 아니라 **"정리 안 된 양"에만 비례**한다. 정리를 잘할수록 싸지는 구조라 운영 동기도 생긴다.

## 3. 질문 방식: 슬래시 명령어 → 멘션

- 팀 니즈: 챗봇처럼 `@봇` 태그 후 자유 질문.
- **입력 방식(멘션/명령어)과 검색 방식은 별개.** 멘션으로 들어온 질문도 기존 search API를 도구로 그대로 재사용한다.
- **(2026-10-26 요구사항) `/정책질문`은 없애고 멘션으로 교체한다.** 처음에는 두 루트를 열어두고 비교할 계획이었지만, 질문 입구는 멘션 하나로 정했다.
  - 비교 실험은 입구가 아니라 **검색 범위**로 한다: 노션(DB + 정책서)만 vs + 미정리 디스코드 (EXPERIMENTS 2-4)
  - `/정책검색`(답변 생성 없이 결과 목록만)은 남긴다.
- 구현 포인트: 스레드 최근 메시지를 맥락으로 첨부, 봇 답변에 답장하면 대화 이어가기(`message.reference`), 입력 중 표시, 2000자 분할, 도구 호출 최대 횟수 제한.
- 멘션 질문은 읽기 전용. 쓰기(정리)는 명령어나 버튼으로만.

## 4. RAG: 남긴다

- 지금 데이터 양(결정 80여 건)만 보면 필수는 아니다. 그래도 남기는 이유:
  1. **비용과 속도가 데이터 양에 비례해 늘지 않게** 하는 장치
  2. 질문은 정책 코드보다 "북마크 조회 API 어떻게 바뀌었지?" 같은 **자연어가 대다수** → 동의어(스크랩/북마크 저장)에 강한 벡터 검색이 유리
  3. 골든셋으로 도입 전후 정확도와 토큰을 숫자로 비교할 수 있음
- 방향: **하이브리드 검색**(키워드 BM25 + 벡터). API 경로·버전 같은 정확 문자열과 의미 유사 표현을 둘 다 잡는다.
- 적용 대상은 **노션 문서 + 논의 DB**. 잡담과 버려진 제안이 섞인 디스코드 원문은 벡터화하지 않는다.
- 노션 정책서는 **정책 ID 단위로 청킹** → 검색 결과가 곧 "어떤 정책 항목인지"가 되어 출처 표시와 제안 위치 지정에 그대로 쓰인다.
- (2026-10-26 측정) 정책서 인덱싱은 기본으로 켠다 (정책서 질문 0/5 → 5/5). 하이브리드는 구현했지만 **리랭크와 같이 쓰면 거절이 약해져** 기본 꺼짐.
  운영(리랭크)에서 정확 문자열을 더 잡으려면 키워드 후보를 벡터 후보와 "따로" 몇 개만 덧붙이는 방식이나 리랭커 거절 기준 조정을 다음에 실험한다.

## 5. 토큰 사용량 모니터링과 한도

- 이미 있음: `data/usage.jsonl` 기록, `/admin/usage` 집계, 답변 하단 토큰·비용 표시, 사용자별 일일 답변 한도(기본 30회), 월 예산 + 80% 알림 + 초과 시 차단 (`app/limits.py`).
- 추가할 것:
  - 루트(명령어/멘션)·피드백 필드를 기록에 추가
  - **Claude Console 워크스페이스 지출 한도**를 2차 안전장치로 설정 (봇 전용 API 키). 한도 도달 시 API가 HTTP 400 `invalid_request_error`를 돌려주므로 봇에서 안내 메시지로 처리
  - 월 예산 견적 공유: **월 예산 ÷ (1회 비용 × 인원)**. 예) 8명 · 월 $10 → 노션 검색 답변만 쓰면 1인 약 80회, 미정리 디스코드 조회까지 붙으면(추정 $0.05~0.1) 1인 약 12~25회. 시범 운영 1~2주 실측 후 다시 계산
  - (고도화) 사용량 모니터링 웹 — `/admin/usage`를 읽는 간단한 페이지
- 운영 방식: 한도를 걸고 시범 운영 → 한도가 끊겼을 때 가치가 더 크다고 판단되면 올린다.

## 6. 서버 배포

- 봇은 디스코드로 **나가는** 연결만 쓴다 → 들어오는 포트·Nginx·도메인 불필요 (API를 외부 공개할 때만 고려).
- 후보: (1) 지금처럼 로컬 Mac (2) **팀이 쓰는 기존 AWS EC2에 컨테이너로 얹기**
- EC2에 얹으면 인스턴스 요금은 그대로라 추가 비용은 원칙적으로 없다. 단, 확인할 것:
  - 여유 자원: `free -m`, `docker stats`. chromadb + 빌드에 메모리 여유 필요 (`DEPLOY.md` 기준 2GB 이상). 임베딩은 로컬 모델 대신 API 사용
  - **운영 서버 보호**: 봇 컨테이너에 `mem_limit`, `cpus` 제한 필수
  - 서버 담당자 합의, `.env` 분리
  - 아키텍처: EC2가 amd64면 서버에서 직접 빌드 (Mac arm64 이미지는 `exec format error`)
- 조건이 맞으면 EC2가 Mac보다 낫다 (상시 가동). 안 맞으면 Mac 유지 또는 무료 VM.
- 같은 토큰으로 두 곳에서 동시에 띄우지 않는다 (명령 중복 처리).
