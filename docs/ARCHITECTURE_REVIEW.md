## 0. 지금 구조 한눈에

```
[Discord] ──▶ bot 컨테이너 ─────────────────────────────────────────────┐

              ├ 승인 → storage → history.jsonl + decisions/*.json (로컬)  │ 같은 ./data 볼륨
              │              └→ notion_store → Notion DB (직접 쓰기)       │
              ├ 승인 후 → spec_reflect (Claude 직접 + Notion 댓글)         │
              ├ 승인 후 → HTTP POST /admin/sync-jobs  ────────┐           │
              └ @멘션·/정책검색 → HTTP /policies/* ───────────┤           │
                                                              ▼           │
                                             api 컨테이너 (FastAPI)       │
                                              ├ notion_loader → Notion 읽기│
                                              ├ spec_index → Notion 읽기   │
                                              ├ Chroma (data/.../chroma)   │
                                              └ 답변·리랭크 (Claude)  ─────┘
                       두 컨테이너 모두 usage.jsonl에 append
```

`CLAUDE.md`는 "봇은 RAG 로직 없이 FastAPI만 HTTP로 호출"이라고 적지만, 실제로는 **읽기 경로만** 그렇다.
**쓰기 경로(요약 LLM, 로컬 저장, 노션 저장, 정책서 반영)는 전부 봇 프로세스 안**에 있고, 봇이 `app.usage`·`app.limits`·`app.rag.spec_loader`를 직접 import한다.
즉 지금은 "봇 = 디스코드 UI + 쓰기 서비스", "API = 읽기 서비스"로 나뉘어 있다. 이 비대칭이 아래 문제 대부분의 뿌리다.

## 1. 워크플로우 — 문제점과 아쉬운 점

### 1-1. 승인 버튼 하나에 5단계가 순서대로 묶여 있다 (`views.py` `approve`)

```
로컬 저장 → 노션 저장 → (3초 뒤) 재인덱싱 요청 → 정책서 매칭(LLM) → 정책서 댓글
```

| 단계 | 실패하면 지금은 | 문제 |
|---|---|---|
| 로컬 저장 | "로컬 저장 오류" 메시지, 끝 | 괜찮음 (아무것도 안 됨) |
| 노션 저장 | 로그 + "⚠️ Notion 저장 실패 (로컬에는 저장됨)" | **다시 시도할 길이 없다.** 로컬엔 있고 노션엔 없는 기록이 생긴다. 다음 재정리는 로컬을 보고 "이미 있음"으로 판단 |
| 재인덱싱 | 로그 warning만 | 다음 승인 때까지 검색에 안 나온다. 아무도 모른다 |
| 정책서 반영 | 디스코드에 "⚠️ 실패" | `scripts.reflect_saved`로 수동 복구만 가능 |
| (중간에 봇 재시작) | 진행 중이던 단계가 사라짐 | 어디까지 됐는지 기록이 없다 |

→ 각 단계가 **"나중에 다시 해도 되는 작업"**인데, 그걸 기억해 두는 장치가 없다. (3절 아웃박스)

### 1-2. "현재 기록"의 기준이 두 개다
- 재정리(Q-7)는 `history.jsonl`의 마지막 버전을 "현재"로 본다 (`storage.current_records`).
- 검색 인덱스는 노션을 "현재"로 본다 (`RAG_SOURCE=auto` → notion).
- `DIRECTION.md`는 **노션이 기준(source of truth)**이라고 했다.

그래서 **PM이 노션에서 상태나 결정 문구를 직접 고치면**: 검색에는 반영되지만, 다음 재정리는 그 수정을 모른 채 로컬 버전과 비교하고, `update`면 PM 수정본을 덮어쓴다. 지금은 테스트 노션이라 드러나지 않았을 뿐, 팀 노션에서는 실제로 생길 일이다.

### 1-3. 동기화가 "승인 이벤트"에만 걸려 있다
- 재인덱싱 트리거가 승인 버튼뿐이다. 노션에서 사람이 고친 것·정책서 수정은 **다음 승인이 있을 때까지** 검색에 안 들어간다.
- 작업 상태(`_jobs`)가 메모리라 API 재시작 시 사라지고, "마지막 동기화 성공 시각"을 알 방법이 없다.

### 1-4. 그 밖에
- 승인 대기 화면이 메모리에만 있어 봇 재시작 시 사라진다 → 요약 LLM 비용을 다시 낸다. (빈도가 낮아 당장은 괜찮음, 우선순위 낮음)
- 여러 결정을 한 번에 승인할 때 루프 중간 실패 시 일부만 저장된다. 결정마다 독립이라 큰 문제는 아니지만, 어떤 건이 됐는지는 디스코드 메시지로만 남는다.

## 2. 아키텍처

### 2-1. 왜 노션 DB와 벡터 DB를 따로 두는가 — 역할을 명시하자

따로 두는 건 맞다. 문제는 **역할이 문서·코드 어디에도 명시돼 있지 않아서** 로컬 파일까지 세 저장소가 서로 "현재 값"을 주장한다는 점이다.

| 저장소 | 할 수 있는 것 | 못 하는 것 | **제안하는 역할** |
|---|---|---|---|
| **Notion DB** | 사람이 읽고 고치고 댓글 다는 화면, 공유, 권한 | 의미 검색, 빠른 대량 조회(평균 초당 3회 제한), 트랜잭션 | **원본(source of truth)** — 현재 유효한 기록 |
| **Chroma** | 벡터·키워드 검색, 빠름, 로컬 | 사람이 보거나 고칠 수 없음 | **파생 읽기 모델(projection)** — 언제든 노션에서 다시 만들 수 있는 캐시. 지워도 잃는 것 없음 |
| **history.jsonl** | append-only, 트랜잭션처럼 한 줄 쓰기, 오프라인 | 수정·조회 비효율 | **쓰기 원장(ledger) + 작업 대기열** — 버전 이력, 아직 노션에 못 보낸 작업 |
| `decisions/<영역>/*.json` | 사람이 파일로 보기 | — | 백업용. history.jsonl과 중복이라 **없애도 됨** |

이렇게 정하면 규칙이 단순해진다.
- 쓰기는 항상 **원장 → (재시도 가능한 작업으로) 노션 → (재인덱싱) Chroma** 한 방향.
- Chroma는 `ingest`만 쓴다. 다른 코드가 Chroma에 직접 쓰지 않는다.
- 재정리의 "현재 기록"은 **노션에서 읽는다** (로컬은 버전 이력·`summarized_until` 용도). 노션 `last_edited_time`이 마지막 승인 시각보다 늦으면 승인 화면에 "⚠️ 노션에서 사람이 수정한 기록" 표시.

> 이 구조는 CQRS(쓰기 모델과 읽기 모델 분리)의 아주 작은 형태다. 이름보다 "Chroma는 지워도 되는 캐시"라는 감각이 중요하다.

### 2-2. 같은 것이 여러 곳에 있다

| 무엇 | 지금 위치 | 문제 |
|---|---|---|
| 설정 | `config.py`(os.environ) · `app/config.py`(pydantic) · `policy_search.py`·`app/usage.py`가 `os.environ` 직접 | 같은 `.env`를 4가지 방식으로 읽음. `NOTION_SPEC_PAGES`는 두 곳에서 **다른 모양**으로 파싱, 모델명은 `CLAUDE_MODEL`/`LLM_MODEL` 두 이름. 값이 틀려도 실행 중에야 알게 됨 |

| 노션 속성 이름 | `notion_store.PROPERTIES` · `app/config.notion_prop_*` | 속성 하나 추가하면 두 곳을 고쳐야 함 |
| LLM 호출 + 사용량 기록 | summarizer · spec_reflect · generator · reranker 각자 | 패턴이 4번 반복. "기록 안 하는 호출 금지" 원칙을 사람이 지켜야 함 |
| usage.jsonl 쓰기 | bot · api 두 프로세스 | 프로세스 간 잠금 없음 (지금 규모에선 실질 위험 낮음) |

### 2-3. 제안하는 목표 구조 — "통로를 하나로"

Boo의 핵심 교훈을 우리 말로 옮기면: **외부 저장소(노션·Chroma·로컬 파일)에 닿는 코드는 한 프로세스, 한 계층에만 둔다.** 봇은 상태가 없는 디스코드 UI가 된다.

```
bot (디스코드 UI만, 상태·NOTION_TOKEN 없음)
 │  POST /summaries          스레드 메시지 → 요약 결과 (LLM)
 │  POST /decisions          승인 → 저장 (+ 후속 작업 예약)
 │  POST /policies/answers   멘션 질문 (지금 그대로)
 ▼
api
 ├ api/routers/        HTTP 입출력만
 ├ services/           유스케이스: summarize, approve, answer, reflect   ← 흐름은 여기
 ├ repositories/       DecisionRepository(노션), Ledger(로컬), VectorStore(Chroma)  ← 저장소 접근은 여기만
 ├ clients/            notion.py(클라이언트 1개 + 재시도), llm.py(호출 + usage 기록 + 한도 체크 1곳)
 ├ worker              아웃박스 처리 + 주기 동기화 (api 프로세스 안의 백그라운드 루프로 시작)
 └ settings.py         설정 1개
```

**효과**
- 노션에 쓰는 곳이 하나 → 재시도·멱등성·로그를 한 번만 구현.
- LLM 호출이 `clients/llm.py` 하나를 지나감 → 사용량 기록·한도 체크를 빼먹을 수 없음 (`CLAUDE.md` 원칙을 코드가 강제).
- usage.jsonl·history.jsonl을 쓰는 프로세스가 하나 → 파일 동시 쓰기 문제 사라짐.
- 봇 컨테이너에 노션 토큰이 필요 없어짐 (권한 최소화).

**하지 않을 것**: Boo처럼 Go로 별도 manager 작성, Postgres·Redis 도입. 지금 데이터 규모(결정 수십~수백 건)에선 비용만 늘어난다. SQLite가 필요해지면 그때 (3-3).

### 2-4. Repository / Unit of Work (cosmicpython 2·6장)를 어디에 쓰나
- **Repository(2장)**: "저장소를 리스트처럼 다루는 인터페이스" 뒤로 노션 API 세부를 숨긴다.
  ```python
  class DecisionRepository(Protocol):
      async def get(self, record_id: str) -> Decision | None: ...
      async def list_by_thread(self, thread_id: str) -> list[Decision]: ...
      async def upsert(self, d: Decision, history: list[Decision]) -> str: ...   # 노션 URL
  ```
  구현: `NotionDecisionRepository`, `JsonlDecisionRepository`(노션 미설정 시), 테스트용 `FakeDecisionRepository`. 지금 `storage.py`의 `if notion_store.enabled()` 분기가 "어떤 구현을 주입하느냐"로 바뀐다.
- **Unit of Work(6장)**: "원장 기록 + 후속 작업 예약"을 **한 번에 성공하거나 한 번에 실패**하게 묶는 단위. 노션은 트랜잭션이 없으니 UoW 대상은 **로컬 원장**이다. 노션 쓰기는 UoW 커밋 뒤 아웃박스가 처리한다.
  ```python
  async with uow:
      uow.ledger.add_version(record)
      uow.outbox.add(Op("notion_upsert", record.id, record.version))
      uow.outbox.add(Op("reindex"))
      uow.outbox.add(Op("spec_reflect", record.id, record.version))
      uow.commit()
  ```
- 순서: Repository 먼저(테스트가 쉬워지고 노션 접근이 모임) → 아웃박스 → UoW는 SQLite로 바꿀 때 자연스럽게.

## 3. 장애 대응

### 3-1. 아웃박스 패턴을 승인 흐름에 적용

dev.to 글의 핵심: **"업무 데이터 저장"과 "나중에 보낼 작업 기록"을 같은 트랜잭션에 넣고, 별도 처리기가 작업을 보낸다.** 우리 경우 그대로 맞는다.

- 업무 데이터 = 원장(history.jsonl)의 새 버전 줄
- 보낼 작업 = 노션 저장 / 재인덱싱 / 정책서 반영
- 처리기 = **쓰기 코드가 있는 프로세스** 안의 백그라운드 루프 (몇 초마다, 또는 새 작업이 들어오면 즉시 깨움). A-6 전까지는 봇, A-6 후에는 api (3-4)

jsonl로 시작하는 가장 단순한 형태: 버전 줄 자체에 작업 목록을 넣으면 "한 줄 쓰기 = 원자적"이라 둘이 어긋나지 않는다.
작업 결과는 **별도 파일**(`outbox.jsonl`)에 쓴다 — 이유와 상세는 3-4.
```json
// history.jsonl (원장)
{"id":"a1b2","version":2, ..., "ops":["notion_upsert","spec_reflect"]}
// outbox.jsonl (작업 결과)
{"op":"a1b2:2:notion_upsert","result":"done","at":"...","notion_url":"..."}
{"op":"a1b2:2:spec_reflect","result":"failed","attempt":1,"error":"429 ...","next_at":"..."}
```
대기 중 = 원장의 `ops`에 있는데 `outbox.jsonl`에 `done`·`dead`가 없는 것. (작업이 늘거나 조회가 느려지면 SQLite 테이블로 — 3-3)

글에서 짚은 함정과 우리 대응:

| 함정 | 대응 |
|---|---|
| 최소 1회 전달 → **중복 실행** | 모든 작업을 **멱등**하게. 노션 생성 전 `기록ID`로 조회해 있으면 갱신(타임아웃으로 "생성됐는데 응답만 못 받은" 경우의 중복 페이지 방지). 정책서 반영은 이미 마커로 중복을 막고 있음 ✅ |
| 계속 실패하는 작업(poison)이 영원히 재시도 | 시도 횟수 + 지수 백오프(1·2·4·8분…), N회 실패면 `dead` 처리 + 디스코드 운영 채널 알림 |
| 처리기 여러 개가 같은 작업을 집음 | 처리기 1개(uvicorn worker 1개)를 전제로 명시. 늘릴 일이 생기면 SQLite 잠금 |
| 전송 지연 | 승인 직후 즉시 한 번 처리 시도 → 실패한 것만 주기 재시도. 사용자 체감은 지금과 같음 |

### 3-2. 케이스별 대응표

| # | 상황 | 지금 | 제안 |
|---|---|---|---|
| F1 | 노션 저장 실패 (429·5xx·타임아웃) | 보고만, 재시도 없음 | 아웃박스 재시도 + 멱등 생성 |
| F2 | **노션 생성은 됐는데 응답 타임아웃** | (재시도가 없어서 우연히 안전) | 재시도 도입 시 반드시 "기록ID로 먼저 조회" |
| F3 | `update_record`가 본문 블록을 지운 뒤 추가하다 실패 | 본문이 빈 페이지 | 본문은 원장에서 언제든 다시 만들 수 있음 → 같은 작업 재시도로 복구. 순서를 "새 블록 추가 → 옛 블록 삭제"로 바꾸면 빈 페이지 구간이 없어짐 |
| F4 | 노션 대량 호출 시 429 | ✅ 라이브러리 내장 재시도(`Retry-After` 존중). A-3에서 `app/notion/client.py` 한 곳에 설정(최대 3회) | — |
| F5 | 재인덱싱 요청 실패·API 다운 | warning 로그, 다음 승인까지 누락 | **주기 동기화(예: 10분)** 추가 → 어떤 누락도 최대 10분. 해시 비교라 비용은 거의 0 |

| F10 | 정책서 반영 실패 | 디스코드 ⚠️ + 수동 스크립트 | 아웃박스 작업으로 자동 재시도 (`reflect_saved`는 그대로 수동 도구로 유지) |
| F11 | 승인 처리 중 봇/API 재시작 | 진행 상태 소실 | 원장에 작업이 남아 있으므로 재시작 후 이어서 처리 |

### 3-3. 저장소를 언제 SQLite로 바꾸나
지금은 jsonl로 충분하다. 다음 중 하나가 생기면 `data/policy.db`(SQLite) 하나로 원장·아웃박스·usage·동기화 작업을 옮긴다.
- 아웃박스 상태 조회가 파일 전체 읽기라 느려질 때
- usage.jsonl이 커져 한도 체크(매 요청 전체 읽기)가 느려질 때
- 원장과 아웃박스를 진짜 트랜잭션으로 묶고 싶을 때 (cosmicpython 6장 UoW를 그대로 적용하는 시점)

Repository 계층을 먼저 만들어 두면 이 교체는 구현 클래스 하나 추가로 끝난다.

### 3-4. 쓰기 실패 방어 상세 (로컬 OK · 노션 실패, 중간 실패, 작업 기록)

**전제: 로컬과 노션은 원자적으로 묶을 수 없다.** 노션은 트랜잭션이 없고, `update_record` 하나도 속성 갱신 → 블록 삭제 N회 → 추가로 여러 번 호출한다.
목표를 바꾼다: **어디까지 됐는지 반드시 남기고(커밋 지점) · 남은 일은 다시 해도 안전하고(멱등성) · 어긋난 건 결국 찾아낸다(대조).**

#### 지금 코드의 빈틈

| 위치 | 상황 | 결과 |
|---|---|---|
| `storage._write_local` | `decisions/*.json` → `history.jsonl` 두 번 씀 | 사이에 죽으면 json만 남음 |
| `history.jsonl` 추가 | fsync 없음 | 줄이 반쯤 써질 수 있음. `storage.load_versions`는 **조용히 건너뛰고**, `JsonlLoader`(`RAG_SOURCE=jsonl`)는 **예외로 인덱싱 전체가 실패** |
| 노션 실패 | `SaveResult.notion_error`가 **메모리에만** 있음 | 디스코드 메시지가 묻히거나 재시작하면 어떤 기록이 노션에 없는지 아무도 모름 ← **가장 큰 문제** |
| `update_record` | 속성 먼저 → 블록 삭제 → 추가 | 중간 실패 시 속성은 새 버전인데 본문은 비어 있음. 겉으로는 성공처럼 보임 |
| 노션 생성 타임아웃 | 생성은 됐는데 응답만 못 받음 | 지금은 재시도가 없어 우연히 안전. 재시도를 넣는 순간 중복 페이지 |
| 원장 읽기 | `storage.load_versions` · `JsonlLoader` · `batch_summarize.already_saved_thread_ids` 3곳이 각자 파싱 | 원장 형식을 바꾸면 3곳이 따로 깨짐 |

#### ① 커밋 지점: 원장 한 줄
- **원장(`history.jsonl`)에 줄이 써지면 승인된 것.** 노션·재인덱싱·정책서 반영은 그 줄의 `ops`에 적힌 후속 작업이다.
- 쓰기: 한 줄을 `write` 한 번 + `flush` + `os.fsync`. 읽기: 깨진 줄은 건너뛰되 **경고 로그 + `/health`에 개수**.
- 원장 읽기는 **한 함수(나중엔 Repository)로 모은다.** `JsonlLoader`·`batch_summarize`도 그걸 쓴다.
- `decisions/*.json`은 없앤다 (원장에서 다시 만들 수 있는 백업).
- 덮어쓰는 파일(정책서 캐시, 알림 상태)은 임시 파일에 쓴 뒤 `os.replace` — 반쯤 쓴 파일이 남지 않는다.

**작업 결과를 원장과 다른 파일(`outbox.jsonl`)에 쓰는 이유**
- 원장 줄을 읽는 코드(`JsonlLoader` 등)가 "모든 줄 = 결정 기록"을 가정한다. 결과 줄을 섞으면 이 코드가 전부 깨진다.
- 결과 파일은 잃어도 된다. 작업이 멱등하니 결과가 없으면 "아직 안 함"으로 보고 한 번 더 할 뿐이다. 그래서 두 파일이 원자적일 필요가 없다 — **원자적이어야 하는 건 "결정 + 해야 할 일" 한 줄뿐.**
- `reindex`는 기록마다가 아니라 전체 작업이라 `ops`에 넣지 않는다. 노션 작업이 하나라도 `done`되면 한 번 요청하고, 주기 동기화(F5)가 나머지를 메운다.

#### ② 다시 해도 안전한 작업 (멱등성)
상태: `pending → done`, 또는 `failed(attempt n, next_at) → … → dead`

| 작업 | 멱등하게 만드는 법 |
|---|---|
| 노션 생성 | 만들기 전에 `기록ID`로 조회 → 있으면 갱신 경로로. 노션은 방금 만든 페이지가 조회에 뜨기까지 몇 초 걸리므로(`policy_search.py` 주석) **첫 재시도는 30초 이상 뒤** |
| 노션 갱신 | DB에 **`버전` 속성 추가**(`ensure_schema`), **맨 마지막에** 쓴다 = 노션 쪽 커밋 표시. 재시도 때 노션 버전이 이미 같으면 `done`. 중간 실패면 버전이 옛 값이라 처음부터 다시 |
| 본문 다시 쓰기 | 기존 블록 ID를 기록 → 새 블록 추가 → 기록한 ID만 삭제. 본문이 비는 순간이 없고, 몇 번 다시 해도 결과가 같다 |
| 정책서 반영 | 기록ID·버전 마커로 이미 중복 방지 ✅ |
| 재인덱싱 | 내용 해시 비교로 이미 멱등 ✅ |

**오류 종류별 재시도 여부**

| 오류 | 처리 |
|---|---|
| 429 | `Retry-After`만큼 기다렸다 재시도 |
| 5xx · 타임아웃 · 연결 오류 | 지수 백오프(1·2·4·8분…), 최대 N회 후 `dead` |
| 400 (select 옵션 없음, 글자 수 초과 등) | 다시 해도 같음 → 바로 `dead` |
| 401 · 403 · 404 (토큰·권한·DB ID) | 설정 문제 → 바로 `dead` + 운영 알림 |

**처리기 위치**: 쓰기 코드(`notion_store`·`spec_reflect`)가 봇에 있는 동안은 **봇 프로세스 안**에서 돈다 (api가 봇의 루트 모듈을 import하면 경계가 더 꼬인다). A-6에서 쓰기 경로를 api로 옮길 때 처리기도 같이 옮긴다. 어느 쪽이든 **처리기는 1개**만 (같은 토큰 봇 2개 금지 · uvicorn worker 1개).

#### ③ 대조 (reconciliation): 마지막 방어선
주기적으로 원장의 현재 버전들과 노션 DB를 비교한다.

| 발견 | 처리 |
|---|---|
| 원장에 있는데 노션에 없음 / 노션 `버전`이 낮음 | `notion_upsert` 작업을 다시 넣음 (**자동 복구**) |
| 노션에 있는데 원장에 없음 (손으로 만든 페이지) | 보고만 |
| 노션 `last_edited_time` > 마지막 승인 시각 (PM 직접 수정) | 오류가 아니라 신호. 다음 재정리 승인 화면에 경고 (F8) |

- **대조는 절대 자동 삭제하지 않는다.**
- 열린 결정: PM의 노션 직접 수정을 원장에 "노션 직접 수정" 버전으로 가져올지. 노션=원본 원칙을 따르면 가져오는 게 맞다 → A-0에서 결정.

#### "DB 로깅"은 두 층

| | 데이터 작업 기록 | 운영 로그 |
|---|---|---|
| 어디 | `history.jsonl`(결정·승인자·버전) + `outbox.jsonl`(작업 결과·실패 이유·시도 횟수) | stdout → docker 로그 (회전) |
| 보관 | 지우지 않음 (감사 기록) | 며칠 지나면 사라져도 됨 |
| 한 줄 | `op, result, attempt, error, notion_url, at` | 노션 호출마다 `op, record_id, version, request_id, status, latency_ms, attempt` |
| 답하는 질문 | "이 기록은 노션에 들어갔나?" | "왜 실패했나?" |

사용자에게 보이는 것
- 디스코드: "⚠️ Notion 저장 실패" → **"⏳ 노션 저장 대기 중 — 자동으로 다시 시도해요"**
- `dead` 발생 시 운영 채널 알림 (예산 알림 웹훅 재사용)
- `/health`: `outbox_pending`, `outbox_dead`, `broken_ledger_lines`
- 수동 도구: `python -m scripts.outbox list | retry <op>`

#### 테스트로 증명하기
가짜 노션 클라이언트에 "N번째 호출에서 예외", "생성은 하고 타임아웃", "429 후 성공"을 주입해서 각 경우 최종 상태(페이지 1개, 본문 온전, 버전 일치)를 확인한다. 기존 `tests/conftest.py`의 가짜 객체 패턴을 그대로 쓴다.

### 3-5. 사용량 측정은 분리하지 않는다
- Boo도 토큰 사용량을 별도 서비스로 뺀 게 아니라, 저장 서비스(manager)의 한 영역(`POST /token`, `GET /token/stats`)으로 뒀다. 분리한 건 "사용량"이 아니라 "저장하는 주체"다.
- 우리는 코드(`app/usage.py`)와 저장소(`usage.jsonl`)가 이미 따로 있다. 남은 문제는 **쓰는 프로세스가 둘(봇·api)**이라는 것뿐이고, A-4(LLM 호출 1곳) + A-6(쓰기 경로 api로)에서 자연히 하나가 된다. 지금 `POST /usage`를 만들면 A-6 때 버릴 코드이고, api가 꺼지면 기록이 사라지는 실패 경로가 하나 늘어난다.
- 별도 서비스로 빼면 한도 체크(매 답변 전)가 그 서비스에 의존한다 → "사용량 서비스가 죽으면 답변을 막나(fail-closed) 보내나(fail-open)"를 정해야 한다. 같은 프로세스면 이 문제가 없다.
- 다시 검토할 때: 다른 봇·프로젝트와 예산을 같이 쓸 때, 파일이 커져 한도 체크가 느려질 때(2026-11-06 기준 2,181줄·580KB → 먼저 SQLite 테이블로).

### 3-6. 노션 직접 수정 반영 — 열린 질문 (나중에 결정)
결정된 것: PM이 노션에서 고친 값이 현재 기록이 된다 (`DIRECTION.md` 2-1 "노션 직접 수정 반영").
"원장에 새 버전으로 가져온다" = 노션 수정도 봇 승인처럼 `history.jsonl`에 버전 한 줄(`origin: "notion_edit"`, `edited_fields`)로 남긴다. 안 하면 재정리가 옛 값과 비교하고, 봇이 덮어쓸 때 PM 수정이 변경 이력에서도 사라진다.

아직 정하지 않은 것:
| 질문 | 후보 | 메모 |
|---|---|---|
| 언제 가져오나 | (a) 필요할 때만: 봇이 그 기록을 건드리기 직전(`/정책정리` 시작, 노션 덮어쓰기 직전) · (b) 대조 작업이 주기적으로 전부 · (c) 가져오지 않고 현재 값만 노션에서 읽기 | (a)가 단순하면서 문제를 다 막는 중간 지점. 검색은 어느 쪽이든 이미 노션을 따른다 |
| 수정을 어떻게 알아채나 | 노션 속성 → 기록 필드로 바꿔 원장 마지막 버전과 **내용 비교** | `last_edited_time`은 분 단위이고 봇 자신의 쓰기에도 바뀐다 (S-1과 같은 교훈) |
| 삭제(휴지통)와 "아직 못 만든 페이지" 구분 | `outbox.jsonl`에 생성 `done`이 있는데 지금 없거나 `in_trash` → 삭제 의도 | 구분 없이 대조가 "없으면 다시 만들기"를 하면 PM이 지운 페이지를 되살린다 |
| 덮어쓰기 직전 충돌 | 노션 현재 값 ≠ 원장 마지막 버전이면 멈추고 알림 (낙관적 잠금) | |
| 수정자 이름 | `last_edited_by`는 사용자 ID만 줌 → 이름은 사용자 정보 권한 필요 | |

## 4. 로깅·관측

| 지금 | 제안 |
|---|---|
| `basicConfig` 텍스트 로그, 봇·API 각자 | `logging_setup.py` 하나. 운영은 JSON 한 줄 로그(`ts, level, logger, msg, request_id, thread_id, record_id, op`) |
| 요청을 따라갈 ID 없음 | 봇이 상호작용마다 `request_id` 생성 → `X-Request-ID` 헤더로 API에 전달 → 아웃박스 작업에도 저장. "이 승인 건이 어디서 실패했나"를 grep 한 번으로 |
| `/health` = Chroma 청크 수 | `last_sync_ok_at`, `outbox_pending`, `outbox_dead`, 노션 도달 여부. 봇도 heartbeat 파일 → compose healthcheck |
| 실패는 로그에만 | 운영 알림 웹훅(예산 알림 웹훅 재사용): 봇 시작, `dead` 작업 발생, 동기화 N회 연속 실패, 예산 80% |
| Docker 로그 무제한 | **compose `logging: max-size: 10m, max-file: 3`** — 공용 EC2 디스크를 채우지 않게 (필수) |

`usage.jsonl`은 앱 로그와 별개로 유지한다 (비용·한도 데이터라 지우면 안 됨).

| A. 현행 | 이미지 1개, 컨테이너 2개(api·bot), `./data` 공유 | 구조 개선 중에는 이걸 유지 |
| **B. 현행 + 운영 보강 (추천)** | A + `mem_limit`/`cpus`, 로그 회전, 봇 healthcheck, 이미지 태그를 git SHA로(롤백용), `data/` 백업, **쓰기 주체를 api로 모아 볼륨을 사실상 api만 씀** | 2-3을 하면 자연스럽게 여기로 감 |
| C. worker 분리 | B + `worker` 서비스 (같은 이미지, `command: python -m app.worker`) | 아웃박스·주기 동기화를 api 안 백그라운드로 시작했다가, api를 여러 worker로 띄우거나 동기화가 답변 지연에 영향을 줄 때만 분리 |
| D. 더 쪼개기 (Postgres·Redis·별도 이미지) | — | 지금 규모에선 불필요. 하지 않음 |

같은 이미지·다른 명령으로 서비스를 늘리는 건 Boo와 지금 compose가 이미 쓰는 방식이라 학습 부담이 적다.
배포 절차(EC2): `git pull` → `docker compose build` → `docker compose up -d` (서버에서 빌드, amd64). 롤백은 이전 SHA 태그로 `up -d`. 자동 배포(5-4)는 수동 절차가 몇 번 안정적으로 돈 뒤에.
